## Exploration: nativewind-setup-tabs

### Current State

**Expo SDK 56** project (React Native 0.85.3, React 19.2.3, TypeScript 6.0 strict) using Expo Router with **flat route structure** (no `(tabs)` group):

- `src/app/_layout.tsx` — root layout: `<ThemeProvider>` > `<AnimatedSplashOverlay>` > `<AppTabs />`
- `src/app/index.tsx` — Home tab
- `src/app/explore.tsx` — Explore tab

**Tab setup** uses platform-specific files via `.tsx`/`.web.tsx`:

- **Native** (`app-tabs.tsx`): `NativeTabs` from `expo-router/unstable-native-tabs` with 2 triggers (Home, Explore), PNG icons from `assets/images/tabIcons/`
- **Web** (`app-tabs.web.tsx`): `expo-router/ui` with `Tabs/TabList/TabTrigger/TabSlot`, custom tab bar with branding and external Docs link

**Styling** is entirely via `StyleSheet.create()` across all 9+ components with:

- Custom theme constants in `src/constants/theme.ts` (`Colors`, `Fonts`, `Spacing`)
- `useTheme()` hook wrapping `useColorScheme()` for light/dark mode
- `global.css` at `src/global.css` with CSS custom properties for web font families

**Build config**: No `metro.config.js`, no `babel.config.js`, no `postcss.config.js`, no `tailwind.config.js`. Uses `app.json` for Expo config.

**Dependencies**: `react-native-reanimated`, `expo-router`, `react-native-gesture-handler`, `expo-symbols`, `expo-image`, `react-native-safe-area-context`, `react-native-screens` — already includes most NativeWind v5 peer deps (missing: `nativewind`, `react-native-css`, `tailwindcss`, `@tailwindcss/postcss`, `postcss`).

**Project uses Bun** as package manager, strict TDD enabled via SDD init.

- **`src/components/app-tabs.web.tsx`** — Add 3rd `TabTrigger` for the new tab; optionally migrate to className
- **`src/app/index.tsx`** — Optionally update to use NativeWind className (demonstrates working setup)
- **`src/app/explore.tsx`** — Optionally update to use NativeWind className

### Approaches

1. **Incremental — Keep flat routes, add NativeWind + 3rd tab** — Minimal restructuring, add NativeWind infrastructure, create a 3rd route file as `src/app/settings.tsx`, add its trigger to both native and web tab bars. New screens use className; existing screens optionally migrated later.
   - Pros: Minimal risk, no route restructuring, clear separation of concerns, preserves existing web tab bar with external Docs link
   - Cons: Existing screens still use StyleSheet (inconsistent until migrated), flat routing may be unfamiliar to some
   - Effort: Low

2. **Full restructure to `(tabs)` group** — Move all routes under `src/app/(tabs)/index.tsx`, `src/app/(tabs)/explore.tsx`, `src/app/(tabs)/settings.tsx`, with `(tabs)/_layout.tsx` using NativeTabs. Requires updating all route references and the root layout.
   - Pros: Standard Expo Router tab pattern, familiar to most devs, cleaner URL hierarchy (`/(tabs)/settings`)
   - Cons: High restructuring effort, NativeTabs doesn't benefit from `(tabs)` group (it uses explicit triggers), breaks deep links if URLs change, need to update all imports and navigation references
   - Effort: High

3. **Unified `expo-router/ui` on all platforms** — Replace `NativeTabs` with `Tabs/TabList/TabSlot` from `expo-router/ui` on native too, styled with NativeWind className. Remove platform split, use a single `app-tabs.tsx`.
   - Pros: Single codebase for tab bar, full className support, maximum NativeWind usage
   - Cons: Loses native iOS/Android tab bar (the user specifically wants native tabs), no liquid glass on iOS 26, no Material 3 on Android
   - Effort: Medium

### Recommendation

**Approach 1 (Incremental).** Here's why:

1. **The current flat structure is the documented pattern for NativeTabs** — `NativeTabs` uses explicit `Trigger` components, not automatic screen detection from `(tabs)` groups. The flat structure is correct, not an accident.
2. **Minimal risk, maximal signal** — The user wants to see NativeWind working, not to redesign the navigation architecture. The fastest path to "NativeWind works with 3 tabs" is to add the infrastructure + one new tab.
3. **Existing screens can stay** — They work fine with StyleSheet. They can be migrated to className incrementally in a follow-up change. No need to touch working code.
4. **NativeTabs tab bar styling is inherently limited** — The native tab bar uses OS-level APIs (`backgroundColor`, `indicatorColor`, `labelStyle`). className doesn't apply to native tab bar elements. This is expected and correct. NativeWind styles the **screen content**, not the native tab bar chrome.
5. **Web tab bar already works** — The web version uses `expo-router/ui` which renders as Views/Texts that WILL support className. This can be migrated later.

**Specific plan:**

- Add NativeWind v5 infrastructure (deps, metro, postcss, global.css, lightningcss override)
- Create `src/app/settings.tsx` with NativeWind className usage as the demo
- Add a 3rd trigger in both `app-tabs.tsx` and `app-tabs.web.tsx`
- Optionally update index.tsx and explore.tsx headers or small elements to use className, proving it works across all 3 tabs
- Keep the existing custom web tab bar layout (branding, external Docs link) but optionally convert its StyleSheet to className

### Risks

- **NativeWind v5 is preview** — Using `nativewind@preview` (or `5.0.0-preview.x`) means API could change. Pin exact versions.
- **lightningcss version pinning is required** — Must override to `1.30.1` in `package.json` or builds may fail with deserialization errors on `global.css`.
- **react-native-css compatibility** — This is a fast-moving nightly/alpha dependency. The expo-tailwind-setup skill references `react-native-css@0.0.0-nightly.5ce6396`. Must verify with actual SDK 56.
- **NativeTabs label limitations** — On iOS 26, unselected label colors cannot be customized (iOS limitation, not Expo). The `labelStyle` prop may not apply unselected colors. Known issue tracked in expo/expo#44029.
- **Safe area with NativeWind** — The `pt-safe` / `pb-safe` utilities have reported inconsistencies with Expo Router's automatic safe area handling. May need explicit `useSafeAreaInsets()` in screens.
- **className on Link/SafeAreaView children** — Known issue in nativewind/react-native-css#233 where direct children of `Link` may not receive className. May need wrapper Views.
- **Bun + lightningcss override** — Need to verify how Bun handles `overrides` in package.json (Bun uses `overrides` like yarn/npm/pnpm, should work).
