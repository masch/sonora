# SDD Proposal: Android ProGuard Mapping Upload

**Change:** `android-proguard-mapping`
**Created:** 2026-07-10
**Author:** SDD proposal executor
**Status:** Draft

---

## 1. Problem Statement

Google Play Console displays the following warning when reviewing App Bundles from the Sonora production pipeline:

> _"No hay un archivo de desofuscación asociado con este App Bundle. Cuando usas un código ofuscado (R8/Proguard), subir un archivo de desofuscación hará más sencillo el análisis y la depuración de fallas y ANR."_

Translation: _"No deobfuscation file associated with this App Bundle. When using obfuscated code (R8/ProGuard), uploading a deobfuscation file makes it easier to analyze and debug crashes and ANRs."_

**Impact:** Currently, every crash and ANR reported through Google Play Console shows obfuscated stack traces (class names like `a.b.c`), making triage significantly harder. Engineers must manually deobfuscate using the locally-generated `mapping.txt` — which is only available if they built that exact release locally.

The Android Gradle build already generates `mapping.txt` at `android/app/build/outputs/mapping/release/mapping.txt` during each production build. This file is simply not captured or uploaded anywhere.

---

## 2. Proposed Changes

### 2a. Capture `mapping.txt` in Makefile Target

**File:** `Makefile`
**Target:** `eas-build-android-release-ci-unsigned`

After the existing `mv` commands for the APK and AAB, add a line to copy the R8/ProGuard mapping file to the output directory with a consistent name.

**How it works:**

- Gradle's `:app:assembleRelease` and `:app:bundleRelease` tasks write `mapping.txt` at `android/app/build/outputs/mapping/release/mapping.txt` (relative to `apps/mobile` after the `cd ..` in the target).
- Add an `OUTPUT_MAPPING` variable (optional, defaults to `sonora-release-mapping.txt`) and a `cp` command.
- This follows the exact same pattern as the existing `OUTPUT_APK` / `OUTPUT_AAB` variables.

```makefile
# New line to add after the existing AAB mv:
cp android/app/build/outputs/mapping/release/mapping.txt $(if $(OUTPUT_MAPPING),$(OUTPUT_MAPPING),sonora-release-mapping.txt)
```

### 2b. Upload Mapping File as CI Artifact (build-android job)

**File:** `.github/workflows/deploy-mobile-android-production.yml`
**Job:** `build-android`

Add a new step after the existing AAB artifact upload to upload the mapping file as an internal GitHub Actions artifact with 30-day retention.

The artifact name will be `android-mapping` and will carry the file through the pipeline.

**Why 30 days:** The mapping file must remain accessible as long as the release it corresponds to is active on Play Console. 30-day retention covers the internal testing window comfortably; the Play Console itself becomes the permanent home after the deploy step.

### 2c. Pass Mapping File Through the Pipeline

The mapping file does NOT need signing, so it can flow directly from `build-android` → `deploy-play-store` without touching `sign-android`.

**Changes needed in `deploy-play-store` job:**

- Add `build-android` to the `needs` array (it currently only `needs: sign-android`)
- Add a download step for the `android-mapping` artifact

### 2d. Add `mappingFile` to the Play Console Upload Step

**File:** `.github/workflows/deploy-mobile-android-production.yml`
**Step:** `Deploy AAB to Google Play Store`

Add the `mappingFile` input to the existing `r0adkll/upload-google-play@v1` action:

```yaml
- name: Deploy AAB to Google Play Store
  uses: r0adkll/upload-google-play@v1
  with:
    serviceAccountJsonPlainText: ${{ secrets.ANDROID_PLAY_SERVICE_ACCOUNT_JSON }}
    packageName: org.masch.sonora.app
    releaseFiles: apps/mobile/sonora-${{ needs.sign-android.outputs.tag_name }}.aab
    track: ${{ inputs.play_track || 'internal' }}
    mappingFile: apps/mobile/sonora-${{ needs.build-android.outputs.tag_name }}-mapping.txt
```

### 2e. R8 Configuration Verification

This is a verification-only task (no code change needed unless issues are found).

The Gradle build generated by `npx expo prebuild` for SDK 56 should have:

- `minifyEnabled true` in the `release` build type
- `proguardFiles` referencing the default ProGuard rules and any project-specific rules

**Verification steps:**

1. Run `npx expo prebuild --platform android --clean` locally
2. Inspect `android/app/build.gradle` → confirm `release` block has `minifyEnabled true` and R8 is enabled (R8 is the default in AGP since 3.4+, which is what SDK 56 uses)
3. Confirm `mapping.txt` is generated during `./gradlew :app:assembleRelease`

If R8 is not enabled in the generated build.gradle (unlikely for Expo SDK 56, but worth verifying), we would need to add a post-prebuild hook or a custom `proguard-rules.pro`. This proposal assumes it works out of the box; the verification task confirms or disproves that assumption.

## 4. Security Considerations

- **`mapping.txt` contains only symbol name mappings** (original class/method/field names → obfuscated names). It does **not** contain source code, secrets, or API keys.
- **Play Console is the intended destination.** Google explicitly provides the `mappingFile` parameter in their upload action for this purpose. The deobfuscation file stays within Google's infrastructure.
- **Internal Actions artifact only.** The mapping file is uploaded as a private GitHub Actions artifact (not a public Release asset). Only repository actors with read access can download it.
- **30-day retention** ensures the artifact auto-expires; the Play Console copy persists for the release lifetime.
- **No exposure of build internals.** The mapping file pairs obfuscated symbols with readable names — useful for crash debugging, useless as an attack vector since no source code or runtime behavior is disclosed.

---

## 5. Non-Goals

- ❌ **No GitHub Release asset upload** — the mapping file is exclusively for Play Console and internal artifact passing. Not a public artifact.
- ❌ **No staging pipeline changes** — staging builds use EAS cloud builds (`eas-build-android-preview-ci`), not the local Gradle approach. Staging is out of scope per user decision.
- ❌ **No custom ProGuard rules** — we use the default R8 configuration from Expo SDK 56. Adding custom keep/proguard rules is a separate concern not triggered by this issue.

## 7. Rollback & Risks

**Rollback:** Fully revertable by reverting the two modified files. No data migration, no schema changes, no irreversible operations.

**Risks:**

- **Low:** If R8 is not enabled in the generated Gradle config (see §2e), the mapping file will not be generated and the artifact step will need `if-no-files-found: warn` instead of `error` for the first deploy until R8 is confirmed active.
- **Low:** The `mapping.txt` corresponds to the unsigned build — but since mapping is deterministic for a given source + R8 config, the signed artifact is an identical binary (signing doesn't re-obfuscate). The mapping is valid for the signed AAB.
- **None:** No secrets in mapping.txt, no public exposure, no behavioral change to the app.

---

## 8. Success Criteria

1. A mapping artifact `android-mapping` appears in the GitHub Actions run after each successful production build.
2. The `deploy-play-store` job downloads the mapping and passes it to the `r0adkll/upload-google-play@v1` step.
3. After deployment, Google Play Console shows a deobfuscation file associated with the uploaded AAB.
4. Crash stack traces in Google Play Console display deobfuscated class/method names.
