# Feature: Offline OSM Map with Drawable References

**Feature ID:** `map-offline-references`
**Branch:** `feat/map-offline-references`
**Strategy:** `ask-on-risk`
**Status:** specs closed for phases 1–2; phase 3 specced but unscheduled.

## Objective

Replace the Leaflet-in-WebView map with MapLibre over self-hostable vector tiles, fed by **two data planes**:

1. **Base plane** — OSM vector tiles (PMTiles) carrying the classes the product decides to show, served from R2 and, in the future, generated with our own Planetiler profile.
2. **Reference plane** — our own GeoJSON documents (per experience or shared), editable from outside the app, drawn as MapLibre style layers on top, tappable to open a content card.

Both planes are rendered by one shared style, so mobile and web never diverge again. Offline packs let a walker keep full zoom without connectivity. A remote flag keeps the current Leaflet map alive during the transition.

## Constraints & Conventions

- Signed-in surfaces follow `AGENTS.md`: `ScreenWrapper`, `ThemedText`, `Icon`, `Button`, `BottomModal`, `useAppTranslation`, `accessibilityLabel` + kebab-case `testID`, `LoadingView` for loading, explicit empty and error states.
- Referenced data model: `map_documents` (document JSON or asset, `scope: global | experience`, style, `zIndex`, `version`) plus `map_document_bindings` (N:N to experiences) so a shared reference is never duplicated per experience.
- `bbox` columns are computed at write time; no PostGIS.
- While both renderers live, `GET /experiences` stays a **superset** and no existing field changes.
- Overlay documents must travel in the offline-cached payload, or tappable references break without network.
- OSM attribution stays visible in every renderer; the derived archive is publishable under ODbL.

El mecanismo nuevo es un bloque `properties.i18n` (`{ es: { label, description? }, en: { … } }`), **excluyente** con `labelKey`/`descriptionKey` y obligado a cubrir todos los idiomas en el schema, así una referencia es autocontenida o por clave y nunca las dos. `withResolvedLabels` ganó un tercer argumento (el idioma activo) con fallback a `DEFAULT_LANGUAGE`, y los dos renderers ahora lo pasan: `buildMapStyle` lo recibe en native y la web lo guarda en un `languageRef` junto al `translateRef` que ya tenía. La ruta de escritura sigue exigiendo traducciones **sólo** para las features que nombran claves, así que el documento autocontenido no toca la tabla. `osm-calamuchita` (36 puntos por clave) y el script de ingesta siguen funcionando sin migración: lo único que cambió ahí son dos lecturas de `labelKey`, que ahora es opcional. El publicador (`apps/api/src/scripts/publish-map-document.ts`) aplana `label`/`labelEs`/`labelEn`/`descriptionEs`/`descriptionEn` a `i18n`, borra los campos de autoría y **no escribe ninguna fila de traducción**: editar un texto es editar el `.geojson` y volver a publicar. Evidencia: shared 34/34, api 12/12 más 11 del publicador, jest de los dos renderers 55/55, `tsc` de api 0 y de mobile 0, y el diferencial de `tsc` en shared —11 errores antes del cambio y 11 después, ninguno nuevo— medido con `git stash`, porque shared ya arrastra errores de tipos en `map-regions.test.ts` y en el cast de `map.test.ts` que no son de este cambio. Riesgo abierto y anotado: un build de la app **anterior** a este cambio dibuja la clave de un documento `i18n`, así que esos documentos no deben publicarse antes del build que los soporta.
- **L50** (la forma final del texto autocontenido, y los dos defectos que la decisión destapó): el humano pidió que los objetos del bloque no repitan nombres de atributos, así que la forma `i18n` (`{ es: { label, description }, en: { … } }`) se reemplazó por **agrupación por atributo** — `label: { es, en }` y `description: { es, en }` — que dice cada nombre una vez por feature (ver D13). El único obstáculo era el choque con `properties.label`, que el resolver escribía como string para que MapLibre lo dibujara: el campo inyectado pasó a llamarse `labelText`/`descriptionText`, y con eso se movieron `style.ts` (`text-field`), `labels.ts`, los dos `toPressReference` y el tipo `MapReferencePress`. Ganancia que no es cosmética: **el archivo autorado es el documento guardado**, así que `publish-map-document.ts` dejó de transformar y ahora sólo valida — se borraron `i18nFor`, `textFor` y la lista de campos de autoría, junto con la posibilidad de que un aplanado se comiera un texto. Dos defectos aparecieron al revisar el camino completo, y los dos habrían dejado la feature a medias: (1) `reference-card.tsx` armaba el cuerpo sólo desde `descriptionKey` y `hasCardContent` tampoco contaba una descripción, así que una referencia autocontenida con descripción y sin link **no abría tarjeta**; ahora lee `descriptionText` y lo cuenta como contenido. (2) en el renderer web, el efecto que aplica los overlays no tenía `language` entre sus entradas —`applyOverlays` es estable y lee el idioma por ref—, así que cambiar de idioma dejaba las referencias en el anterior; se agregó la dependencia. Ese segundo arreglo **no tiene test**: medido con una sonda mínima, `useTranslation` de react-i18next no despierta a sus suscriptores en jest-expo (`i18n.language` cambia y el componente sigue renderizando el idioma viejo), así que un test del redibujado sería teatro; queda anotado como hueco. Evidencia de la forma nueva: shared 34/34 (incluye el rechazo de un bloque de idioma incompleto y de un documento con bloque y clave a la vez), api 74/74 entre ruta, seeds y publicador; `tsc` de api y mobile en 0 y el diferencial de shared sin errores nuevos.

- **L51** (el resultado de la review nativa del PR #595, y los dos hallazgos que llegaron después): cuatro lentes más un refuter cerraron en `correction_required` con **tres defectos causados por el candidato**, cada uno reportado por más de un lente — `--dry-run` documentado y nunca parseado, así que `--publish --dry-run` publicaba igual; `keyBased` contando sólo `labelKey`, con lo que una feature con `label` más `descriptionKey` pasaba como autocontenida y esquivaba la negativa del seed; y un cambio **no pedido** al mensaje del guard de `seed-data.ts`, que perdió el nombre del entry point. La corrección entró en 50 líneas de diff (presupuesto 200) y un validator dirigido confirmó los ocho hallazgos resueltos sin regresiones, con una nota honesta: la mitad del hallazgo de `keyBased` del lado del loader quedó sin confirmar porque `seed-maps.ts` no estaba entre los tres caminos de corrección que el provider fijó. Después, dos hallazgos más del mismo cierre: CodeRabbit señaló que el seed escribía documento, borrado de bindings e inserción en **tres sentencias sueltas** — idempotencia no es atomicidad, y un fallo en el medio deja un documento publicado sin bindings, o sea el mapa invisible para su experiencia; ahora es una transacción, tipada `NodePgDatabase` porque es el tipo que puede prometerla, con un doble de test que **lanza si una escritura se escapa** del handle (verificado por mutación). Y las reglas de link e imagen vivían privadas en la ruta: se movieron a `apps/api/src/map-documents/policy.ts`, compartidas por los dos caminos de escritura. Primer intento equivocado y corregido por el humano: las puse en `@sonora/shared` argumentando "una sola casa", cuando el objetivo era un módulo que ambos caminos de la api importen — nada fuera de la api llama esas dos funciones, y el dato que la regla necesita (`MAP_LINK_ALLOWED_HOSTS`, `isAllowedHttpsUrl`) sí sigue en shared porque el cliente lo usa para decidir si dibuja el botón.
