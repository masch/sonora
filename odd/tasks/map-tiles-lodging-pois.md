# Map tiles: lodging POIs (cabins next to the Salón)

A walker compared the same place in OSM and in our map: the toilets are there now, the cabins
next to the Salón are not. The cause is three gaps stacked (profile, style, sprite), and this
slice closes all three so a lodging POI is drawn from the tile like any other.

Branch: `feat/map-tiles-lodging-pois`, stacked on `feat/map-tiles-building-names` (PR #587,
unmerged, review burned). Delivery is the human's: push and PR.

## Specs

- `S1` — the user's request, verbatim: "detecte algo que falta de los mapas de OSM, si bien ahora
  se ven los POI de los baños, no se ven los iconocs de la cabañas que están junto al salon. Te paso
  como se ven en OSM y en nuestra version no parecen los iconos de las cabañas, porque es?"
- `S2` — the answer must be the basemap's: profile + style + our own sprite. The app's OSM
  reference layers are an existing alternative and were explicitly not chosen.
- `S3` — nothing drawn today may disappear: the toilets, the "Salón" label, the area names and
  every kind the `pois` filter already admits keep working, and the added kinds are additive.
- `S4` — no admitted kind may be iconless. A kind in the `pois` filter that resolves to an icon the
  published sprite does not carry is a test failure, not a blank square on a phone. This is the
  invariant whose absence produced the bug.
- `S5` — the sprite stays a single published sheet: no version segment in its url, the same four
  objects (`sprites/light{,@2x}.{json,png}`), and 1x and 2x in step. What that buys is stated where
  it is true and only there: staging uploads write `must-revalidate`, so the new icons arrive as
  bytes at the same key; production writes `immutable` for a year, so publishing the extended sheet
  there is **out of this slice** and its decision (serve `must-revalidate`, or give the base a
  version segment) is recorded in `docs/map-assets-pipeline.md`.
- `S6` — the fix is reproducible without a new dependency and without a machine-only rasterizer:
  the icons are generated by a repository script that a CI test can run.

## Log

- `L1` — "detecte algo que falta de los mapas de OSM, si bien ahora se ven los POI de los baños, no
  se ven los iconocs de la cabañas que están junto al salon. Te paso como se ven en OSM y en nuestra
  version no parecen los iconos de las cabañas, porque es?"
- `L2` — Diagnosis, from data rather than from the style: the cabins are **7 ways** `building=yes` +
  `tourism=guest_house` **without a name** (OSM API, bbox `-64.7400,-32.2140,-64.7300,-32.2060`:
  638440640, 641, 642, 644, 647, 649, 651), 4 of them in tile `16/20982/38967` and 3 in
  `16/20983/38967`. Three gaps, each sufficient on its own: (1) the profile drops every POI that is
  neither a point nor a named polygon, and patch `0007`'s `AREA_POI_KINDS` has only `toilets`,
  `drinking_water`, `bench` — tile `16/20983/38967` carries **0 POIs** today; (2) the style's `pois`
  filter admits 36 kinds and **no** lodging kind, so even the named lodging POIs already in the
  archive are invisible — tile `16/20977/38959` carries `apartment`, `hotel` and four `chalet`
  features that draw nothing; (3) `icon-image` is `["get","kind"]` and the sprite's 53 icons carry no
  lodging glyph, so a kind without an icon draws nothing at all. A fourth constraint was found while
  measuring: the filter is `zoom >= min_zoom`, and the pool's chalets carry `min_zoom` 17 against a
  z16 archive, so the kinds we admit have to land at min zoom 16 or they can never appear.
- `L3` — Decision, the user's: the basemap fix (profile + style + our own sprite), not the app's OSM
  reference layers. Regional census from Overpass over the Calamuchita bbox, which is what sized the
  kind set: `chalet` 8, `guest_house` 7 (all unnamed), `camp_site` 3, `hotel` 3, `hostel` 3,
  `apartment` 1. So the set to carry is those six plus the vocabulary the profile already knows
  (`motel`, `bed_and_breakfast`, `caravan_site`, `alpine_hut`, `wilderness_hut`), mapped to two new
  icons — a bed for the lodging kinds and a tent for the camping ones.
- `L4` — `resort` is out, and the render check is what said so. It was in the kind set on the theory
  that "Centro Umepay" (`kind=resort`, name in the tile) was invisible for the same reason as the
  hotels — it was — but admitting it costs an area name: the check failed `not drawn: Huerta Madre`,
  and a style copy with only `resort` removed passed on the same tile with `Centro Umepay` gone and
  `Huerta Madre` back. `S3` decides it: nothing drawn today may disappear, so the eleven kinds became
  ten and `resort` stays a follow-up with its min zoom, not part of this slice. The new test also
  surfaced a pre-existing gap it does not fix: `townhall` is admitted by the filter and the pinned
  sheet has no `townhall` glyph, so it draws nothing — recorded as the one known exception, asserted
  to be exactly that one, so a new gap cannot hide behind it.
- `L5` — Measured, rebuilt and verified: the archive is **881 143 B** (+175 over 880 968) with the same
  nine vector layers, and `archive-features.test.ts` went from `0 > 0` (red, before patch `0008`) to
  green on both tiles — `16/20982/38967` now carries 4 `guest_house` POIs and `16/20983/38967` carries
  3, where it carried **none**. All seven come out at `min_zoom` 17, exactly like the toilets beside
  them, which is what makes them appear at the same overzoom the walker was already using.
- `L6` — Writing the runbook found a fact that changes `S5`: the asset upload is **not** the same policy
  in both environments. Staging writes `public, max-age=0, must-revalidate`; production writes
  `public, max-age=31536000, immutable` (Makefile, `api-upload-map-assets-*`). These keys carry no
  version segment, which was harmless while the sheet was a frozen third-party artifact and stopped
  being harmless the moment we started appending to it: a changed `sprites/light*` published to
  production is a no-op for every device that already cached it, so the new icons would silently not
  appear. `S5` was rewritten to say what is true (staging) and to put the production decision where it
  belongs, and `docs/map-assets-pipeline.md` carries the two ways out — serve the assets
  `must-revalidate` in production too, or give the sprite base a version segment — with neither taken
  here, because publishing to production is not this slice.
- `L7` — Published to staging and verified against what it serves, not against the build directory.
  `make api-upload-map-assets-staging` put the extended sheet in the bucket (the served
  `sprites/light.json` answers with **55** icons, `lodging` at `x:0,y:114` and `camping` at `x:19`,
  plus the `@2x` pair), then the archive and the style went up in the same version: `/config` reports
  **`archiveBytes: 881143`**, and the served style admits 47 kinds with `icon-image` mapping the seven
  lodging kinds to `lodging` and the four camping ones to `camping`. The `published` job's steps were
  run here against the published object — the API named the url, the download was 881143 bytes with
  the `PMTiles` magic, and `CI=true bun test scripts/map-tiles` with `MAP_TILES_ARCHIVE` pointing at
  it came back **126 pass, 0 fail**, including the render check of the four measured tiles and the
  cabins on both tiles. The GitHub job itself needs the branch pushed and a PR, which is the human's
  call; the steps it runs are the ones that just passed.
- `L8` — Native review (`review-add676f119503c79`, tier medium, four lenses) raised one BLOCKER, and it was
  right: `R4-001` — "the extend step is not idempotent as `T3` requires". I had written it to _refuse_ a
  sheet that already carried the icons and documented that as idempotence, and even pinned the refusal
  with a test; but a documented operator target has to survive being run twice, and a process killed
  between the 1x and 2x writes left an atlas whose only recovery was a forced re-fetch. The fix inverts
  the behaviour: a sheet that already documents the icons is **repainted in place** — the drawing is
  deterministic, so a re-run is byte-identical and it heals a box a partial write left blank — and only a
  sheet without them grows a row. Verified on the real sheet: `make map-assets-icons` twice leaves both
  `light.png` and `light.json` byte-identical (`md5sum -c`), and two new tests pin the re-run and the
  repair. The lesson is the one this whole slice is about: the assertion I wrote tested my intent, not the
  property the target needs.
